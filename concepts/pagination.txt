---

# 🔹 What is Pagination?

**Pagination** is the process of splitting a large dataset (e.g., thousands of products, users, or posts) into smaller chunks (pages).

👉 Instead of sending **10,000 records in one API response**, we send maybe **10–50 records per page** along with metadata (`count`, `next`, `previous`).

---

# 🔹 Why Do We Use Pagination?

1. **Performance** → Prevents overloading the server & client by fetching too much data at once.
2. **User Experience** → Improves speed and makes data browsable in pages.
3. **Network Efficiency** → Reduces bandwidth usage.
4. **Scalability** → Handles large datasets easily.

---

# 🔹 Pagination in DRF

DRF provides **3 main pagination styles**:

---

## 1. **PageNumberPagination**

* Works like a book → `page=1`, `page=2` etc.
* Very intuitive for users.
* Commonly used in blogs, e-commerce, etc.

**Example**

```
/api/products/?page=2
```

**Settings**

```python
REST_FRAMEWORK = {
    'DEFAULT_PAGINATION_CLASS': 'rest_framework.pagination.PageNumberPagination',
    'PAGE_SIZE': 10
}
```

**Response**

```json
{
  "count": 125,
  "next": "http://127.0.0.1:8000/api/products/?page=3",
  "previous": "http://127.0.0.1:8000/api/products/?page=1",
  "results": [
    {"id": 11, "name": "Product 11"},
    {"id": 12, "name": "Product 12"}
  ]
}
```

**Use case** → When users navigate sequentially like pages in a blog, forum, or shop.

---

## 2. **LimitOffsetPagination**

* Works like SQL → `LIMIT x OFFSET y`.
* More flexible: you can control **how many results** and **from where to start**.

**Example**

```
/api/products/?limit=10&offset=30
```

👉 Returns 10 products starting from the 31st record.

**Settings**

```python
REST_FRAMEWORK = {
    'DEFAULT_PAGINATION_CLASS': 'rest_framework.pagination.LimitOffsetPagination',
    'PAGE_SIZE': 10
}
```

**Response**

```json
{
  "count": 125,
  "next": "http://127.0.0.1:8000/api/products/?limit=10&offset=40",
  "previous": "http://127.0.0.1:8000/api/products/?limit=10&offset=20",
  "results": [
    {"id": 31, "name": "Product 31"},
    {"id": 32, "name": "Product 32"}
  ]
}
```

**Use case** → Best for APIs consumed by **mobile apps or frontend frameworks** where you need fine-grained control (like infinite scrolling).

---

## 3. **CursorPagination**

* Uses a **cursor (encrypted position)** instead of page numbers or offsets.
* **More performant** for large datasets because it avoids expensive `OFFSET` queries in the database.
* Provides **stable ordering** (usually by `created_at`).

**Example**

```
/api/products/?cursor=cD0yMDI1LTA4LTE2KzA1JTNBMTAlM0EwMC4wMDBa
```

**Settings**

```python
REST_FRAMEWORK = {
    'DEFAULT_PAGINATION_CLASS': 'rest_framework.pagination.CursorPagination',
    'PAGE_SIZE': 10
}
```

**Response**

```json
{
  "next": "http://127.0.0.1:8000/api/products/?cursor=cD0yMDI1LTA4LTE2KzA1JTNBMTElM0EwMC4wMDBa",
  "previous": null,
  "results": [
    {"id": 101, "name": "Product 101"},
    {"id": 102, "name": "Product 102"}
  ]
}
```

**Use case** → For **infinite scrolling feeds** (e.g., Twitter, Facebook, Instagram), where new data keeps coming and consistent ordering matters.

---

# 🔹 Quick Comparison

| Pagination Type      | Example URL           | Pros ✅             | Cons ❌                     | Best Use Case                   |
| -------------------- | --------------------- | ------------------ | -------------------------- | ------------------------------- |
| **PageNumber**       | `?page=3`             | Easy to understand | Fixed page size            | Blogs, forums                   |
| **LimitOffset**      | `?limit=10&offset=20` | Flexible, SQL-like | Expensive for large offset | Apps, APIs needing fine control |
| **CursorPagination** | `?cursor=abc123`      | Scalable, stable   | Not human-readable         | Social feeds, infinite scroll   |

---

👉 In real projects:

* **Simple sites** → `PageNumberPagination`
* **Data-heavy APIs** → `LimitOffsetPagination`
* **Infinite scroll / real-time apps** → `CursorPagination`
